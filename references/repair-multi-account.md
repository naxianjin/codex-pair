# 双账号维修交接要求

当前仅支持两个用户已打开的官方 CLI 原窗口 A/B，不支持多人扩容。最新结论及历史测试边界见 [测试汇总](validation-summary-20261019.md)；下文历史版本号不代表当前包版本。

以下 v1.1.3 记录为历史，曾新增 OpenAI A × DeepSeek B 基础真实验收；权限环境和未验证范围见 [verification.md](verification.md)。下文是维修要求，不表示每项在本轮都重新执行过。

普通使用现已改为当前窗口 start/accept 配对，见 onboarding.md。本文件保留维修与历史验收要求；下列本机目录、开发分工和维修 worktree 不是普通协作的固定账号或必需启动流程。

这是双账号维修规格与验收清单。实现已提供状态解耦、成员账号路由、relay/manual 接口、项目内目录和安装校验；实际支持的 CLI 模式以目标机器的真实验收为准，不能凭文档或测试替代。用户需要交给 CLI 时，将本文件与项目路径一并转交。不索取或输出账号令牌，不复制认证文件。

## 先修正安装与角色发现

源码以当前项目目录为准，不依赖特定磁盘路径。检查参与 CLI 的实际 CODEX_HOME，不能仅凭窗口名或预设文件夹猜账号。参与窗口仅支持官方 Codex CLI 的 OpenAI 官方账号与已配置 DeepSeek API，不扩展其他提供方；DeepSeek 边界与验收见 [deepseek.md](deepseek.md)。

此前维修使用过多个独立 CODEX_HOME；它们只是历史安装实例，不决定参与窗口。运行时各窗口的 home 从自身环境读取。需要自动发现技能时在该环境安装同版 skill；也可在现有会话显式读取邀请指向的同一份 SKILL.md，无需为刷新技能重开窗口，但这不等于已安装。分别备份旧 skill，只安装技能文件，不复制认证、配置、会话或缓存。检查引用和哈希一致，不声称安装即已加载。

`scripts/install_skill.py --source <源码根目录> --home <实际A目录> --home <实际B目录> --home <其他待安装配置目录>` 只安装 `skills/codex-pair`。已有技能先改名保存在各 home 的 `codex-pair-skill-backups/`，输出可恢复备份路径；白名单仅包含 SKILL.md、agents、scripts、references、tests，跳过认证/config 和 Python 缓存。暂存和落盘副本逐文件 SHA-256 与源包比较。先解析每个 home 的实际位置并按真实路径去重：同一目录的 junction 不重复安装；目录名称相似但不是实际 CODEX_HOME 的清理工具或主题目录不算安装目标。安装器拒绝技能目录重定向，不改登录、账号配置或会话。

清理旧版必须另有用户授权。在新版安装和发布包核验后，按精确路径将旧技能备份、旧 ZIP、独立解压副本送入系统回收站，并保留清单；不永久删除，不清理 Git 历史、已登记 worktree、协作状态或登录配置。磁盘安装不表示现有会话已加载新版，旧桥也不会自动重载。

普通 start 建立新一轮，第一个成功登记的窗口是数据库 A；接受本轮 CODEX_PAIR_JOIN_V1 邀请的是 B。上一轮角色不决定新一轮角色。只有明确 start --resume-pair <ID> 才保留旧绑定；口头换角色无效。原协作有未决工作时禁止自动换绑，并发发起由项目锁返回同一邀请。

## 共享状态与账号分开

1. 新增共享 --state-root，默认 `<项目>/.codex-pair/state`，每个协作在其下拥有独立 ID 子目录。协作 worktree、交接、日志和归档也留在项目 `.codex-pair/` 内。写入前验证真实路径和本地 Git 排除，不覆盖已跟踪文件。
2. join 新增 --member-codex-home，分别保存 A、B 的实际账号目录。会话验证、观察、queue 和托管恢复始终使用目标成员目录。任何账号失败不得回退到另一账号。
3. Store 接收独立状态位置；TransportPool 按成员建立客户端并将账号目录纳入客户端缓存键；claim/complete/signaling 信封传递状态位置，不能将账号目录误当状态目录。
4. 更新当前拒绝项目内状态的校验：仅允许已验证的专用协作子目录，拒绝越界、认证路径和源文件覆盖。 SQLite/附件/日志不得被 Git 跟踪。
5. 旧单账号记录保留原目录，显式迁移时备份、停派发并检查处理中消息；不静默移动活动数据库。旧成员缺账号字段时继承原账号目录，不猜另一个账号。

## 不依赖账号互联的本地桥接

两个账号不需要互相登录，也不要求服务端提供账号之间的消息功能。传递任务用本机共享数据库；让目标模型开始下一轮仍需要它自身可用的 CLI 接口。

优先方案：单一 dispatcher 读取共享 SQLite，按目标成员的 CODEX_HOME 调用其 queue/app-server，持久化后投递，消息 ID 原子领取去重。实测 A→B→A 后再启用自动模式。

若中央 dispatcher 无法可靠接入两套会话，增加每账号本地 relay：A relay 在 A 的原账号环境运行，B relay 在 B 的原账号环境运行；各自只领取发给本成员的 outbox，调用本账号的 queue/app-server 并写回回执。共享数据库负责路由与仲裁，relay 的租约和原子状态更新避免重复投递；复用现有 unknown 对账和领取门，不能遇到超时就换账号重发。

若本账号自身接口也无法自动唤醒已打开的 TUI，文件信箱只能实现手动交接：将消息 ID 和最小通知写入 `.codex-pair/handoffs/`，用户在目标 CLI 输入领取命令，再由该 CLI 读取数据库执行。不创建托管会话替代原窗口；遗留托管记录仅保留历史。必须明确显示“手动交接”或“托管会话”，不能宣称原有两个窗口已经自动通信，也不模拟键盘。

无需新增网络服务即可覆盖同一 Windows 用户的场景。暂停后停止新增投递，已经接受的任务按现有协议收尾；停止保留记录和代码。守护程序与 relay 使用原账号权限，不自动审批。

## 开发与验收

维修任务按依赖、允许路径、工作树安全和成员负担登记；方案细化、审查、测试和整合准备也计入 effort，不按历史角色包办。只有已有独立工作树才并行，同树串行。通信未成立前使用用户转交的提交 SHA 交接，不能依赖正在维修的消息桥。

测试至少覆盖两个不同 home 的路由与身份错误、共享数据库并发领取、错误账号不回退、重试与 unknown、relay 重启、暂停/停止、项目内 worktree 不污染 git status、旧状态迁移，以及所有已确认安装副本一致性。

最终用两个独立 CODEX_HOME 的真实账号会话完成并行任务、提问答复、提交交付和整合。分别报告单元测试、后台真实 CLI、可见双 TUI 和手动降级的结果；未执行的项目明确列出。交付准确的 A/B 启动、加入、dispatcher/relay、状态查看和停止命令，不保留已知字段的占位值。
