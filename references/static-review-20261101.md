## 需要处理的发现

以下行号属于上述固定候选，公开仓库的已发布源码可能不同。P1表示进入相关动态验收前应优先处理；P2表示功能或测试契约存在缺口。修复建议和补测条件均未执行。

### R1 / P1：按任务暂停没有进入本地工具门禁

位置：`scripts/pair_control_runtime.py:223,245`；`scripts/pair_recovery.py:1319,1329`。

触发条件：某任务已经领取并在原窗口执行，只对该任务登记暂停，协作整体仍为running，也没有成员级或全组暂停。

`_pause_record`仅在pair范围修改协作状态。`_matching_controls`按传入的task_id识别任务级暂停，但PreToolUse和Stop分支只传member，未传task_id，也没有由准确turn/tool绑定反查任务。因此在没有其他门禁时，下一次本地工具调用不会匹配这条任务暂停。UserPromptSubmit和claim检查了任务范围，不能覆盖已经开始的回合。

应将准确任务绑定接入受支持工具的门禁；绑定不明时记录不确定状态。补测须覆盖“已领取后暂停、下一工具被拒绝、无关任务按范围继续”，不能只测试排队前暂停。现有 `tests/test_followup_v14.py:36` 和 `tests/test_native_control_v14.py:32` 主要覆盖全组暂停。

### R2 / P2：Windows未加引号的路径会使管理命令识别失败

位置：`scripts/pair_control_runtime.py:28-40,244-245`。

管理命令识别使用默认POSIX规则的 `shlex.split`。合法的Windows无空格路径，例如 `D:\Python\python.exe D:\project\scripts\pair.py ...`，会被拆成 `D:Pythonpython.exe` 和 `D:projectscriptspair.py`，无法通过准确解释器/脚本路径比较。全组暂停时，这类原本允许的诊断或恢复管理命令会落回业务门禁并被拒绝。

本轮只在可信宿主调用标准库确认上述分词结果，没有调用候选识别函数或真实Hook。带完整引号的路径不属于这个示例，不能将结论扩大为所有Windows命令失效。

应统一生成并识别受支持的Windows命令形式，保留原有组合命令拒绝条件。现有 `tests/test_followup_v14.py:53`只检查拒绝shell组合，尚需正常命令、中文/空格目录、引号和无引号路径的正向用例。

### R3 / P2：未接受旧邀请的提前返回绕过目标一致性检查

位置：`scripts/pair_windows.py:213-223,250-252`。

触发条件：项目已有只有A、尚未接受的邀请，窗口再次用不同goal执行start。扫描到旧邀请后直接返回它，后面的goal一致性检查不会运行。来自同一窗口时还会返回role=A，使调用者容易把旧目标当作本次新目标。

复用同目标的并发start有必要；不同目标应明确报告原邀请及冲突，保留用户选择，不能直接把请求替换成旧目标。已有并发start和“旧B开始新轮次变A”的测试不覆盖“只剩一个成员、未接受邀请、目标改变”的分支。

### R4 / P2：三、四成员的额度择优只比较一对

位置：`scripts/pair_balance.py:61-69`；调用处 `scripts/pair_core.py:660-670`。

实现先从所有候选中选数值差最大的一对，再判断这对额度是否可比。未知额度被用于选对时按0处理。一旦选中的一对不可比，直接回退负担均衡，不再检查其他可比较成员。

静态例子：A=80%、B=30%，两者新鲜、不同账号池且周期/桶一致；C未知；复杂任务effort=8。选对会落在A/C，再进入工作量回退。如果B的加权负担最小，可能将复杂任务交给B，即使A/B相差50个百分点。

两窗口20个百分点阈值已有测试；新增三、四窗口混合未知、不同桶和共享池用例，并明确“部分额度未知是否让全组放弃已知额度比较”的策略。这里记录的是确定的分支行为和需求覆盖风险，不把未运行例子称为实测分配结果。

### R5 / P2：新协作主入口仍默认共用原工作树

位置：`scripts/pair_windows.py:51-56,233-237`；`tests/test_windows.py`中的 `test_invite_uses_current_windows_arbitrary_homes_and_no_worktrees`。

指南第06章第7项要求各执行窗口默认使用独立Git工作树。当前start/accept会沿用已有同仓库工作树，否则回到目标项目根目录；主入口不创建成员工作树。旧测试还明确要求不创建worktrees目录。

两窗口从同一项目启动时会共用工作区，调度器再按工作区占用串行化。串行保护应保留，但这不满足指南要求的默认并行准备。独立工作树能力存在于旧init路径，不能据此宣称当前start路径已经默认使用。

应补齐新入口的工作区准备及准确绑定流程，同时保留原会话cwd、不搬动已有脏改动；无法隔离时明确记录降级原因。补测须通过start/accept验证两个独立工作区和实际重叠执行，不能仅测底层worktree创建函数。

### R6 / P1：旧回归仍有与schema14和恢复契约冲突的断言

位置：`tests/test_handoff_balance.py:317-328`；`tests/test_multi_account.py:244`；`tests/test_windows.py:374`等。

例一：旧规划测试暂停后直接 `control('running')`，随后期望生成下一规划任务；新版 `scripts/pair_core.py:1144-1145`明确拒绝该路径，要求登记恢复核查。例二：旧迁移测试断言user_version=13，当前迁移终点在 `scripts/pair_core.py:277`是14。

AST搜索发现13处直接调用running的测试位置，必须逐个判读；其中 `tests/test_diagnostics_v14.py:66`本来就是验证拒绝的负向测试，不能批量改掉。全文搜索还发现5份旧测试文件保留schema13终态断言。

这些是静态可确认的测试契约冲突，不是本轮执行失败数量。应保留原测试目的，补齐新的恢复来源和证据夹具；不能直接修改数据库放行、删除断言或把所有13机械替换为14。
